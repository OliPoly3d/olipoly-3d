# Project identity and production queue correction

Prepared November 4, 2026. **Approved, applied to OliPoly ERP Test and published privately on November 4, 2026.** The original pre-application review is retained below; the current execution record is in [APPLIED.md](APPLIED.md). This is a focused correction to the existing test workspace, not a separate tool or a replacement for the Finance milestone.

## Observable behavior

- All work and each Production tab show a shared list of every approved, unfulfilled project, including approved work awaiting release.
- Each row identifies the project number, customer, title, accepted quantity and release/production state. Opening the row selects that project's own release and run controls.
- Recording approval opens Production. Approval does not reserve material; Release remains a separate action.
- Existing accepted `Q-000001` / `OP-000001` remains linked without renaming either record. The UI displays `OP-000001 · Original quote Q-000001`; searching either reference finds it.
- After the migration, a new connected request receives `OP-0000001`-style numbering at first successful save. The same identifier occupies the existing quote-number and order-number fields as the project advances. Revision, send, acceptance and release do not allocate another number. Existing legacy Q records retain their real links.
- Cancelled/archived/removed projects do not return their numbers. Database sequence allocations are not rolled back: gaps after a failed transaction are intentional. The app cannot reset the sequence or remove reservation records.

## Exact migration for approval

Target: **OliPoly ERP Test**, `llscjdyiiatmuqhilube`, only.

File: [20261105003419_ops_test_permanent_project_numbers.sql](../../supabase/ops-preview/migrations/20261105003419_ops_test_permanent_project_numbers.sql)

The filename was generated by Supabase CLI; its timestamp is UTC. It stays outside the normal live migration runner.

The migration adds `ops_preview_private.project_number_reservations` with a unique numeric suffix, origin and allocation date, RLS enabled, no client access. It seeds reservations from both Q and OP references in jobs, quotes, orders, public tracking, accepted snapshots, events and inventory history. The sequence starts above those references, its previously issued high-water mark and the recorded quote/order counters. Existing identifiers, totals, snapshots, payments and stock amounts remain unchanged.

It replaces four existing functions:

| Function | Change |
| --- | --- |
| `allocate_order_number()` | Use the shared non-recycling sequence, retain an allocation reservation, minimum seven digits without truncation |
| `ops_preview_commit(...)` | Allocate OP on first save, reuse it on later operations; derive invoice suffix correctly from either legacy Q or new OP |
| `respond_to_quote_public(...)` | Accept new OP quote identities and use that same identity for the order; retain legacy Q acceptance behavior |
| `public_order_tracking_lookup(...)` | Recognize longer OP numbers and normalized leading zeros while retaining actual Q-to-order lookup |

The same tables/queries used by the existing workspace continue to supply orders. No new customer login or standalone finance database is added. Sequence privileges are removed from ordinary client roles; existing authorized server functions remain the allocation authority.

## Expected effects, risks and recovery

Apply during a brief pause in test writes: the migration locks workspace/jobs/quotes/orders while seeding. It preserves existing test records and does not reset the workspace. Before applying, compare hosted definitions of the four functions with the reviewed baseline/connected versions; stop if they changed. Inspect the target and migration history explicitly.

Capture the pre-application schema, reference/counter values and row counts for comparison. After application, verify the reservation table's access controls, allocator/lookup definitions and new-project behavior using the test login; run advisors and report inherited findings separately.

The static UI can display existing legacy references before migration, but permanent new-project numbering requires this migration. Do not describe it as active before it is applied. No database application or Site publication has occurred for this correction.

Recovery should preserve all reserved numbers and the sequence's highest issued value. Prefer a reviewed forward fix; stop writes if acceptance fails. Do not drop the reservation table, reset the sequence, delete new OP records, or restore an old Q-only acceptance function over them. Sequence advancement is nontransactional, so even an aborted migration can leave a harmless gap. Any destructive restore requires its own approval and reconciliation of numbers issued since the backup.

## Live replacement gate

This test script is **not an approved live migration**. At live cutover:

1. Inventory every legacy Q/OP reference, existing link, counter and retained reference in invoices, receipts, events, archived/cancelled work and any imports/backup history. Identify manually reserved ranges or numbers absent from retained records; never guess that missing means available.
2. Preserve original references and actual relationships. Do not infer links by replacing Q with OP or combine two legacy projects because they share a suffix.
3. Reserve both namespaces conservatively; choose the new OP high-water mark above all known used/reserved numbers and counters. Test allocations never set the live sequence and test sample rows are not imported.
4. Pause old ERP number creation and imports, take a recoverable backup, perform a final delta/reference check and audit all number-creating paths before enabling the replacement. Leaving an old quote/order allocator active defeats a unified numbering scheme.
5. Apply a separately reviewed live migration/import with explicit authorization. Verify unique references, relationship counts, customer links, immutable financial records and no omitted historical data. Keep a cutover manifest and test rollback/recovery without reusing issued numbers.
